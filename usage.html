Usage guide

Using SealForge

This guide will help you prepare your token, grant signing permissions and follow your jobs. You can work in the browser or automate signing with the API.

Run SealForge with Docker

Three published images on a Linux host you control.

Images

  • docker.io/sealforge/web — web application and REST API
  • docker.io/sealforge/worker-jsign — signing worker and token access
  • docker.io/sealforge/nginx — TLS reverse proxy

Before you start

  • A Linux host with Docker Engine and Compose 2.24.4 or newer.
  • A compatible signing token, certificate and PKCS#11 module.
  • A TLS certificate for your hostname and the CA bundle used for timestamp verification.
  • Persistent PostgreSQL and artifact storage with a backup plan.

Install

  1. Prepare the host

    Create the deployment directory, then add the TLS, PKCS#11 and trust directories and the release Compose files.

  2. Configure secrets

    Set the PostgreSQL and worker database passwords and the public URL in the deployment environment file.

  3. Pull and start

    Pull the release images and start the production stack with the USB-token override.

  4. Complete setup

    Open the setup page, use the setup code from the web logs, create the administrator account and enroll MFA.

  5. Enroll and sign

    Enroll the token, grant a Signing Permission and sign a test file.

Quick start

docker pull docker.io/sealforge/web:<version>
docker pull docker.io/sealforge/worker-jsign:<version>
docker pull docker.io/sealforge/nginx:<version>

export SEALFORGE_IMAGE_VERSION='<version>'
export SEALFORGE_WEB_IMAGE_DIGEST='<web digest>'
export SEALFORGE_WORKER_IMAGE_DIGEST='<worker digest>'
export SEALFORGE_NGINX_IMAGE_DIGEST='<nginx digest>'

docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  -f docker-compose.usb.yml up -d

Use the version and digest values from the release notes. The web logs print the one-time setup code after startup.

USB token hotplug

Physical-token hotplug needs systemd and udev on the host. Install the helper once, then keep the USB override last when starting the stack:

sudo deploy/scripts/sealforge-hotplug-install.sh install

docker compose -f docker-compose.yml -f docker-compose.prod.yml \
  -f docker-compose.usb.yml up -d

If the host pcscd service already owns the reader, stop it while SealForge uses the token. The release installer configures this hotplug chain by default; pass --no-usb to skip it.

Local TLS

Production uses the certificate and key in certs/fullchain.pem and certs/key.pem. For a local demo or lab only, set SEALFORGE_TLS_MODE=local-self-signed to generate a self-signed certificate.

Set up SealForge

Installation steps

  1. Open your installation

    Open the HTTPS address of your SealForge deployment.

  2. Complete initial setup

    Use the setup code supplied by the deployment's startup output at /setup. Create the administrator account and enroll TOTP MFA.

  3. Store recovery information safely

    Keep recovery codes offline. Sign in with your account and authenticator; do not share an administrator account with a team or pipeline.

Before the first signing job

  • The worker must reach the intended token through compatible middleware.
  • The token needs an eligible code-signing certificate and its corresponding private key.
  • Timestamp and trust configuration must be ready.
  • The requesting user or API client must have a usable Signing Permission.

Having an administrator role or a certificate listed in inventory does not automatically grant permission to sign.

Set up your token and permissions

Use a fresh MFA check when the application requests one for sensitive changes.

Tokens and certificates

  1. Open Administration → Tokens and choose Add Token to begin.
  2. Use Scan & Select to choose the intended token.
  3. Provision the PIN in the browser's encrypted PIN step.
  4. Complete Verify & Save and review the returned certificate inventory.

Enrollment requires authenticated inventory with certificates. There is one active token; its certificates are separate choices, not an implicit default.

Users, clients and Signing Permissions

Manage people in Users and pipeline identities in Clients. In Signing Permissions, select one user or API client and one certificate.

Grant API clients only the scopes they need. Certificate use still requires its own permission. Review or revoke permissions when responsibilities change.

Use Settings for the application's retention and operational policies. Keep vendor middleware available to the deployment rather than putting a PIN or a default certificate selector in a script.

Create and follow a signing job

  1. Open Jobs

    This is your personal signing workspace. Use New Job to open the submission dialog.

  2. Select a Signing Permission

    Choose the certificate permission granted to your account. If none is usable, ask an administrator before uploading.

  3. Choose your file and sign

    Select an accepted file, complete any requested MFA check and use Sign to submit.

  4. Check the result

    Use the job row's Details action for status, completion and failure information. Keep the Job ID when asking for help.

Your jobs and the system view

The personal Jobs page shows your interactive jobs. Administrators use Administration → Jobs for the system-wide view.

Browser downloads: The Jobs page can submit and monitor interactive requests, but does not yet offer downloads. The API download endpoint only serves jobs created by that API client. Use the API workflow below when you need automated result collection.

Pipeline workflow

Automate signing with the API

Create a dedicated client with submit, status and download scopes and an explicit Signing Permission. Keep its key in your pipeline's secret storage.

1. Discover the permission and submit

Set SEALFORGE_URL, SEALFORGE_API_KEY, SIGNING_PERMISSION_ID and ARTIFACT_PATH for your own instance. Obtain the permission ID from the first request.

curl --fail-with-body \
  --header "Authorization: Bearer ${SEALFORGE_API_KEY}" \
  "${SEALFORGE_URL%/}/api/v1/signing-permissions"

curl --fail-with-body \
  --header "Authorization: Bearer ${SEALFORGE_API_KEY}" \
  --form "artifact=@${ARTIFACT_PATH}" \
  --form "assignmentId=${SIGNING_PERMISSION_ID}" \
  "${SEALFORGE_URL%/}/api/v1/signing-jobs"

A successful submission returns HTTP 201 and job metadata including jobId. Save that identifier as JOB_ID for the following requests.

2. Poll, then download the verified result

curl --fail-with-body \
  --header "Authorization: Bearer ${SEALFORGE_API_KEY}" \
  "${SEALFORGE_URL%/}/api/v1/signing-jobs/${JOB_ID}"

# Run only after status is ReadyForDownload.
curl --fail-with-body \
  --header "Authorization: Bearer ${SEALFORGE_API_KEY}" \
  --output signed-artifact \
  "${SEALFORGE_URL%/}/api/v1/signing-jobs/${JOB_ID}/download"

Handle a failed, cancelled, blocked or expired job as a failed release step. Do not download merely because submission succeeded. Preserve the original file type when naming the downloaded artifact.

Downloads are owner-checked and subject to retention. Keep your release copy in your own artifact store rather than treating the signing workspace as permanent storage.

Permission missing?

Confirm the user or API client is enabled, the permission is enabled, and the selected certificate is usable. An API scope is not a substitute for certificate permission.

PIN or token unavailable?

Ask an administrator to inspect the token and key-access details. Do not send PINs through a ticket, query string or pipeline log.

API request rejected?

Check the Bearer header and scopes, use exactly one valid assignmentId, and keep the same client identity for status and download. Unknown or foreign jobs return 404; a disallowed or not-ready download returns 403.

Need more detail?

Use your deployment's /api-docs and operating guide. Remove credentials and identifying audit data before sharing diagnostics.
